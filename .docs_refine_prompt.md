# Docs refinement prompt (for codex / any coding agent)

You are refining the docs of this repo. Goal: cut bloat, sharpen voice, make every sentence earn its place. Think YC: one idea per sentence, concrete over abstract, no marketing adjectives, no flourish.

## Scope (edit in place)

- `README.md`
- `docs/architecture.md`, `principles.md`, `roadmap_demand_led.md`, `extending-oak.md`, `dev_experience.md`, `contract_tests.md`, `onboarding.md`
- `docs/design/workspace.md`, `storage_and_archive.md`, `lifecycle_and_lease.md`, `memory.md`, `dispatch_and_pool.md`, `tenant.md`
- `packages/oak-*/README.md`, `packages/oak/README.md`, `packages/oak-dev/README.md`

## What to cut

1. **Restatement.** If a paragraph says the same thing as the heading or the prior paragraph, delete it.
2. **Marketing adjectives.** `robust`, `seamless`, `comprehensive`, `production-grade`, `framework-neutral`, `cloud-neutral`, `first-class`, `loved`, `clean`. Strip the adjective unless it carries unique information.
3. **Parallel-construction triplets.** "X · Y · Z" or "framework-neutral, cloud-neutral, production-grade". Pick the most concrete, drop the rest.
4. **Trailing flourishes.** Sentences that summarize what was just said: "That's the whole filter.", "This is the principle.", "And that's the design." Delete.
5. **"Why this compounds" / "Operational rule:" / "Operating rule:" footers** under every principle. Keep at most one per principle, and only if it adds info the rule itself doesn't.
6. **FAQ filler.** Questions that exist to introduce a paragraph. If the answer stands alone, drop the question.
7. **Cross-reference tables that duplicate the file tree.** A reader can `ls docs/`. Don't list every file.
8. **Aspirational hedging.** "We may", "we might", "in the future we'd like to". Either commit (and ship) or cut.
9. **Numbered-list bloat.** Lists with more than 7 items, or items longer than 2 lines each. Collapse or convert to prose.
10. **Worked-example tables that show the same shape 3 or more times.** One example is enough.
11. **YC-application leakage.** Anything that reads as pitch deck ("credibility-driven OSS in the spirit of httpx"). Cut, or move to a single line in `architecture.md`.
12. **Self-referential meta-commentary.** "This doc is the orientation", "read in order", "every PR should be measured against".

## Voice rules

- Present tense for what exists. Past tense for design decisions made. Future tense only for explicitly demand-gated items.
- Active voice. No "is designed to", no "is built to". Just "does X".
- One idea per sentence. If a sentence has more than one comma plus a dependent clause, split it.
- No em dashes. No en dashes. Hyphens only for compound modifiers.
- No semicolons in prose unless disambiguating a list.
- Engineer-to-engineer tone. Assume the reader has built something before.

## Self-directed audit (in addition to the strip list above)

Read each doc and flag anything that doesn't belong in an OSS project's public docs, then cut or reframe it. Use your own judgment. Common patterns to look for:

- **Private-context residue.** Anything that only makes sense to the original maintainer or their company: internal product names, internal team references, internal Slack/Linear/Notion links, internal pricing thinking, "our YC application says...", references to a private companion repo or research dir. If a sentence reads as if leaked from an internal doc, cut it.
- **Pitch-deck language.** Investor framing, market-size claims, competitive-positioning paragraphs, "we believe X will be a $1B market". OSS docs explain the software, not the business.
- **Roadmap as marketing.** "We're going to be the Kubernetes of agents." Either ship it or don't mention it.
- **Founder voice creeping in.** First-person plural "we" when it means "the maintainer" rather than "the project's contributors". Replace with the project name or rewrite passively.
- **Decisions framed as battles won.** "We chose X over Y because Y is dead". Keep the technical reason for X, drop the dismissal of Y. Punching down at competitors signals immaturity in OSS.
- **Aspirational claims unsupported by the code.** If the doc promises a feature, grep the code. If it isn't there, either implement it or move the doc claim into a roadmap section that's clearly labeled as future.
- **Audit/findings/TODO scaffolding.** Section headings like "Open questions", "Decisions to make", "Audit findings", "Next concrete actions". These belong in an internal planning doc, not public OSS docs. Either resolve the item inline or delete the section.
- **Self-congratulation.** "This is the deepest contract a toolkit can make." Cut. Let the reader decide.
- **Excessive cross-referencing.** Docs that mostly link to other docs without saying anything themselves. If a doc is 80% link and 20% content, fold it into the doc it links to.
- **Repeated vocabulary lessons.** Re-defining "session", "tenant", "Protocol" in every file. Define once in `architecture.md` or `principles.md`, link from elsewhere.
- **Unstable wire-format-style claims about things that aren't wire formats.** Only the JSONL layout, storage paths, OTel attribute names, and Protocol method names are "forever". Other things shouldn't claim that level of stability.
- **CLAUDE.md / Codex / AI-tooling internals.** This is OSS. Readers don't care what AI tool built it. Remove any references to the build process.
- **Inconsistent terminology.** If `archive` is called "session log" in one doc and "event archive" in another, pick one and unify.

For each cut or reframe, the test is: would an outside contributor reading this for the first time gain anything from it? If no, remove. If maybe, sharpen until yes.

If a whole file fails the test, propose deleting it. Don't delete unilaterally. List it in your final report so the user can confirm.

## Process

1. Read each file end-to-end first. Don't edit mid-read.
2. Edit in place. Use multi-line replacements. Don't be afraid of large diffs.
3. After each file, re-read it cold and ask: "would a 10-person AI-native startup founder skim this and learn the architecture in under 90 seconds?" If no, cut more.
4. When done, run:
   ```
   wc -l README.md docs/**/*.md packages/*/README.md
   rg -n '-|-|seamless|robust|comprehensive|production-grade|That'\''s the' README.md docs/ packages/*/README.md
   ```
   Both should be tight. Zero hits on the grep. Fix any survivors.
5. Stage everything. Do NOT commit. Print the diff stat (`git diff --stat`) so the user can review.

## Acceptance bar

A reader who has never seen oak should be able to:
- Read the README in 90 seconds and know what oak is, what it ships, and what it doesn't.
- Read `architecture.md` in 5 minutes and understand the layering plus every Protocol's job.
- Read any `docs/design/*.md` in 3 minutes and know the Protocol shape plus backend strategy.

If a paragraph doesn't contribute to one of those outcomes, cut it.
